I've signed up to Jeremy Howard's new course Solve It with Code.

I first encountered Jeremy via his Fast.ai courses that I explored a few years ago. I found his approach refreshing in the sense that it was non-traditional, but also extremely well considered and pedagogically informed.

I'd describe his approach as "Notebook Driven Development" and his style as literate, exploratory, functional and terse. Apart from his coding style, I suspect his style is not too different from a research developer or data scientist in this regard, the main difference is that he uses notebooks to generate first class coding artifacts using tools like nbdev which he coauthored.

He's new course follows a similar vein from what I can tell, but creates a new environment similar to a Jupyter notebook but with the inclusion of AI prompts as first class cell types and some interesting workflows to leverage LLMs in a smart way.

What I've found so far looking at the 2023 Solve It course is Jeremy and his team are using LLMs in novel and interesting ways I haven't seen used else where. Two smart things I've seen so far is LLM prompts only provide notebook context above, allowing for useful iteration of ideas while controlled context. The other really smart (and seemingly obvious in retrospect) idea is to edit a LLM's previous response to guide future responses. This is really powerful and not really used in other LLM assisted tools I've used like Cursor and Claude Code.

Coming from a Clojure background, Jeremy's exploratory style was immediately familiar to me and I'd describe Notebook Driven Development as a subset of Repl Driven Development that Lisp programmers are familiar with. I'd say there are pros and cons with both approaches and that you could probably create a programming language and environment

If I compare Python notebook driven development I'd summerise as follows:

Pros:
- Notebooks are much more literate and visual
- Notebook tooling is excellent
- Python ecosystem is huge and has a large selection of libraries for every occasion

Cons:
- Producing actual artifacts is a bit awkward and requires a bunch of annotations and a complation step
- Well importing notebooks as modules can be done in Python, it breaks most of the notebook tooling
- Many Python libraries don't work that well in a notebook environment compared to a similar library in Clojure. Testing a FastAPI handler for instance requires running the server, whereas in Clojure a handler is modelled as a pure function.
- This style of programming is much more effective with a expression based language which Python is not, making certain things a bit more awkward than they need to be.

I do however think a REPL driven approach is more effective than other approaches I've tried such as TDD. It would be an interesting experiement to see if you could have your cake and eat it with this style.

If you could have notebooks as first class modules with more cell types (markdown notes, code notes, code and tests), python tooling that recognised the notebooks and resolve notebook imports and libraries that were more functional and value based that would go a long way.
